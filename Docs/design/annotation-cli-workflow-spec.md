# 批注 CLI 完整工作流改进规格

确认日期：2026-10-15。

状态：用户已通过 grilling 访谈确认行为。本轮仅保存规格，尚未开始实现。

关联工单：[GitHub Issue #53](https://github.com/jinghonh/LaTeX-Review/issues/53)。

调查基线：`036c0d6df8f495edb83c11776ec5a1cda7fd74d1`。

## 1. 目标与范围

本规格覆盖用户提出的七项问题。首要使用者是通过 CLI 工作的 AI 代理。

目标工作流：发现报告 → 查询内容 → 提交批注 → 核对结果 → 连续应用建议。

支持分阶段实现。各阶段必须保持已有单处建议和精简输出兼容。

本规格补充并修订 [2026-10-11 批注接口规格](../annotation-improvements-plan.md)。
旧规格要求源码版本变化后拒绝旧建议。本规格增加经过校验的重新定位。
旧规格没有承诺多处建议和批量源码应用。本规格明确增加这些能力。

## 2. 当前事实与问题

下表记录调查基线的行为，不代表本规格已经实现。

| 用户问题 | 调查结论 | 改进方向 |
| --- | --- | --- |
| 批量 JSON 字段没有文档 | 契约中已有部分字段说明，但批量入口缺少完整字段表和示例 | 在使用入口集中说明字段和定位规则 |
| 字段错误不具体 | 校验将未知字段、缺失字段等合并为笼统错误 | 提供逐项、逐字段诊断 |
| 原文匹配规则不透明 | 批注定位匹配展示文字；源码建议匹配原始源码；引用命令未在输入端展开 | 显式区分输入类型，并解释失败原因 |
| 源码单元边界不可见 | 简单表格已有独立单元格；复杂结构会降级；精简读取默认 50 条 | 展示原始源码、区间、可靠性和分页状态 |
| 多处修改和连续应用困难 | 建议绑定整文件指纹和正文版本；应用一条后，其他旧建议可能失效 | 多处建议、整组应用、逐处状态与重新定位 |
| 报告目录难发现 | 工作进程提供 `/api/report`；入口根路径不提供该接口 | 统一报告发现，并修正技能指引 |
| 批量结果不便核对 | 批量结果不带锚点原文和行号；`batch --full` 也不补充这些字段 | 保留精简默认值，增加显式 JSON 核对选项 |

只读调查使用临时论文复现了连续应用问题。
同时创建 `beta → better` 和 `gamma → delta` 两条建议。
应用第一条后，第二条在旧正文中因文件指纹变化而失败。
重新解析后，第二条仍因正文版本和源码区间校验而失败。
第二条建议的原文 `gamma` 本身没有改变。

已有 `--content --full` 可以完整读取内容。
已有 `--review-record` 可以导出包含位置和原文的 Markdown。
这两项已有能力不替代本规格要求的入口改进和 JSON 核对选项。

## 3. 已确认行为

### 3.1 JSON 字段与文档

1. 提供完整批量字段表，标明必填字段、类型、默认值和适用操作。
2. 说明标签字段为 `tags`。
3. 说明旧的单处建议使用 `suggested_replacement: {original_chunk, replacement_chunk}`。
4. 提供普通文字、公式定位、单处建议和多处建议的可运行 JSON 示例。
5. 解释 `unit_id`、`formula`、`quote` 和其他定位字段的组合规则。
6. 同步 CLI 文档和 latex-review 技能，避免使用者阅读源码才能提交。

多处建议的具体字段名和新 CLI 参数名在实现时确定。
文档不得把尚未实现的字段写成可用接口。

### 3.2 字段校验与诊断

1. 批量错误返回输入项 ID、字段路径和具体原因。
2. 分别报告未知字段、缺失字段和类型错误。
3. 嵌套对象错误指向具体嵌套字段。
4. 诊断提供修正所需的信息，例如允许的字段或预期类型。
5. 批量调用保留已有逐项结果和提交模式。

### 3.3 展示文字与源码输入

1. 批注定位显式支持展示文字输入和 LaTeX 源码输入。
2. 调用者声明输入类型，工具返回实际使用的匹配方式。
3. 已有调用保持展示文字定位语义。
4. 源码输入必须支持含 `\ref`、`\eqref` 的可靠定位。
5. 源码输入和 `original_chunk` 均保持精确匹配，不自动忽略空白。
6. 工具不根据猜测选择输入类型或歧义位置。

定位失败时，工具区分未找到、出现多次和超出单元范围。
工具提供实际源码、空白差异和有限候选位置。
诊断说明引用转换等已能确定的失败原因，不把推测作为确定原因。
候选位置不能替代成功定位。

### 3.4 源码单元与读取

1. 查询直接展示完整 `raw_latex`、源码范围和源码定位可靠性。
2. 查询明确展示源码单元边界。
3. 查询说明返回数量、分页状态和完整读取方法。
4. 可用于定位和替换的原文不得被静默截断。
5. 每处替换必须位于一个可靠、连续、单文件的源码单元内。
6. 跨单元修改拆成多个明确替换项，再通过一条建议或整组应用处理。

复杂表格或宏无法可靠定位时，工具明确说明降级原因。
源码定位不可靠时，工具不得自动回写。
本规格不要求取消已有浮动体子单元，也不改变主变更计数。

### 3.5 一条建议包含多处替换

1. 一条批注可以携带多个明确替换项。
2. 每项绑定自己的单元、原文、替换文本和源码位置。
3. 多个替换项可以属于不同文件。
4. 保留旧的单处建议格式。
5. 工具只应用列出的替换项，不隐式执行全文搜索替换。

例如，一次符号重命名可以作为一条批注提交。
调用者仍须列出需要替换的各处源码。
每处替换分别遵守单元边界和精确匹配规则。

### 3.6 整组应用、冲突和逐处状态

“整组”指本次调用显式选中的全部建议及其尚未应用的替换项。
选择一条多处建议时，默认纳入该建议全部尚未应用的替换项。
选择多条建议时，冲突检测和去重覆盖所有选中项。

1. 提供整组预检和差异预览，并支持跨文件应用。
2. 默认整组成功；任一替换项冲突时，整组不写入源码。
3. 提供显式部分成功模式，允许同一建议内部逐处成功。
4. 相同位置且内容完全相同的替换去重，并返回关联关系。
5. 其他重叠替换全部标记为冲突，不按输入顺序选择赢家。
6. 部分成功模式跳过冲突项，只应用独立且通过校验的替换项。

工具分别记录每处替换的状态。
没有替换项完成时，建议整体状态为“未应用”，结果保留逐处失败原因。
一条建议十处替换成功九处时，整体状态为“已部分应用”。
只有全部替换完成时，建议才显示“已应用”。
重复引用同一去重替换的建议必须得到一致状态。
重试跳过已应用项，只处理尚未完成的项。
应用状态不自动改变批注的解决状态。

默认整组模式发生源码写入或应用记录持久化失败时，恢复本次已写入的内容。
显式部分成功模式以每处替换协调源码和应用记录，不回滚其他已成功项。
恢复不得覆盖外部并发修改。
恢复未完成时，明确返回实际修改状态和待恢复信息，不声称整组已回滚。
跨文件提交、并发检测和中断恢复的实现方案须在编码前细化。

源码提交后若报告重建失败，工具保留源码修改。
结果必须明确返回“源码已修改、报告待更新”。
工具不得把报告重建失败描述成源码未应用。

### 3.7 连续应用与重新定位

1. 应用一条建议后，工具自动适配由本工具已记录修改影响的剩余建议。
2. 自动适配必须重新校验位置、原文和可靠性。
3. 原文变化、重叠或定位歧义导致受影响项拒绝应用。
4. 用户或其他程序修改源码后，要求调用者显式重新校验。
5. 外部修改通过重新校验后，剩余建议才可继续使用。
6. 不得仅删除文件指纹或正文版本检查来实现连续应用。

重新定位不授权工具自动修改建议内容。
失败项必须返回具体原因，并保留已完成项的状态。

### 3.8 报告发现

1. CLI 支持从服务 URL 或当前论文目录发现具体报告。
2. 按当前论文目录筛选后，唯一匹配时自动选择。
3. 多篇论文或两类报告仍有歧义时，返回候选并要求明确指定。
4. 不自动选择最近使用的报告。
5. 区分常驻入口、报告工作进程及其代理路径。
6. 用户不必翻阅重建配方才能得到报告目录。

已有发现路径应写入文档：

- `latex-review-local list` 中的 `papers[].slots.live.directory` 和 `papers[].slots.diff.directory`。
- 工作进程的 `/api/report`。
- 入口代理路径 `/papers/{paper_id}/{live|diff}/worker/api/report`。

入口根路径 `/api/report` 不是报告发现接口。
技能不得再根据任意服务端口直接拼接该根路径。
发现逻辑遵守 [本地入口服务 ADR](../adr/0002-resident-local-entry.md) 的代理约定。

### 3.9 批量结果核对

1. 默认输出保持精简。
2. 新增显式核对选项，在同一份 JSON 结果中增加核对字段。
3. 每项返回输入项 ID、线程 ID、单元 ID、文件和行号。
4. 每项返回完整锚点原文和建议原文。
5. 多处建议逐处返回核对信息。
6. 核对结果反映本次操作完成时的状态。

JSON 核对不依赖另外读取 Markdown 文件。
已有 Markdown 复核记录可以继续使用。
工具不得把不存在的源码位置伪装成确定行号。

## 4. 分阶段交付

```mermaid
flowchart LR
 A[阶段一：字段、诊断和核对] --> B[阶段二：发现、定位和单元查询]
 B --> C[阶段三：多处建议和整组应用]
 C --> D[阶段四：重新定位和完整流程验收]
```

| 阶段 | 交付内容 | 主要验收 |
| --- | --- | --- |
| 一 | 字段文档、具体字段错误、显式 JSON 核对 | 无须阅读源码即可构造请求；结果可逐项对应 |
| 二 | 报告发现、两种定位输入、源码单元查询 | 正确处理引用命令、空白差异、边界和发现歧义 |
| 三 | 多处建议、跨文件整组应用、去重冲突、逐处状态 | 默认整组成功；显式逐处成功；重试不重复应用 |
| 四 | 工具自身修改自动适配、外部修改显式校验 | 连续应用有效；冲突拒绝；完整 CLI 工作流通过 |

## 5. 验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A1 | 批量请求含未知嵌套字段 | 错误指出输入项、完整字段路径和允许字段 |
| A2 | 批量请求缺少字段或字段类型错误 | 两类错误可以明确区分 |
| A3 | 按示例提交公式、标签和单处建议 | 不需要阅读实现即可成功 |
| A4 | 展示文字和源码分别定位含 `\ref`、`\eqref` 的句子 | 各自按声明类型定位；回执说明匹配方式 |
| A5 | 源码仅差空白、匹配零次、匹配多次或超出单元 | 不猜测匹配；诊断返回实际源码及具体原因 |
| A6 | 查询超过 50 个单元和较长源码单元 | 可发现分页并完整读取；边界、区间和可靠性明确 |
| A7 | 查询行间公式、简单表格和复杂表格 | 独立单元可见；不可靠结构明确降级 |
| A8 | 一条建议包含跨单元、跨文件的多个替换项 | 各项分别绑定可靠单元；可以整组预检和应用 |
| A9 | 默认整组应用中有一项冲突 | 所有文件均不写入 |
| A10 | 一条建议十项中九项通过，开启部分成功 | 九项应用；一项保留失败原因；整体为已部分应用 |
| A11 | 重试 A10，并修复剩余项冲突 | 不重复应用前九项；最后一项成功后整体为已应用 |
| A12 | 两项替换完全相同，另两项重叠但替换不同 | 前者去重并保留关联；后者全部报告冲突 |
| A13 | 同文件先后应用两条互不重叠建议 | 第二条可经校验继续应用，无须重新创建建议 |
| A14 | 工具修改导致剩余建议重叠、原文变化或歧义 | 受影响项拒绝应用，其他项状态不被误报 |
| A15 | 外部程序修改源码 | 不自动适配；显式重新校验通过后才继续 |
| A16 | 源码提交成功但报告重建失败 | 源码保留；明确返回报告待更新 |
| A17 | 从入口 URL、工作进程 URL 或当前论文目录发现报告 | 返回正确报告目录；歧义时返回候选 |
| A18 | 批量操作开启 JSON 核对选项 | 输入项、线程、位置和完整原文可逐项核对 |
| A19 | 使用旧单处格式和默认精简输出 | 保持兼容 |
| A20 | 跨文件应用途中写入或持久化失败 | 默认整组恢复；部分成功模式保留其他成功项；结果准确说明实际状态 |
| A21 | 部分成功模式下全部替换项均失败 | 整体为未应用，逐处保留失败原因 |
