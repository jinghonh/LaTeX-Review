# 批注提交性能

用户于 2026-10-14 确认本规格。目标适用于本机 HTTP 报告服务，从客户端提交到持久化成功并完成绘制，P95 不超过 200 毫秒。

## 验收范围

1. 单条新增、回复、编辑、解决、重新打开、删除和元数据更新。
2. 批量预检和批量提交分别计时，每批最多 100 条、请求最多 1 MiB。
3. 每篇论文最多 1 万条批注、100 个正文版本。当前真实论文另行复测。
4. 同一论文最多三个客户端，合计每秒五次提交。修订冲突明确返回，不能静默覆盖。
5. 首次加载、换版准备、CLI 冷启动、快照、审计、导出、源码操作和报告重建单独计时。
6. 发起提交的客户端满足 200 毫秒目标。其他客户端每两秒检查变化并读取增量。

```mermaid
flowchart LR
 A[验证正文并建立索引] --> B[客户端提交]
 B --> C[校验修订号与幂等编号]
 C --> D[SQLite事务与WAL持久化]
 D --> E[返回受影响线程]
 E --> F[更新卡片与标记并绘制]
```

## 实现

原存储每次恢复、校验、复制并重新打包全部历史正文。新存储按线程和正文版本分别读取。
SQLite 使用完整同步和 WAL。事务同时提交变更、修订号、变更记录和请求收据。较大的请求收据压缩存储，减少重复正文的写入量。
服务持有空闲连接，避免每个请求关闭最后一个连接时触发全量 checkpoint。后台执行被动 checkpoint。
正文准备完成后，普通提交复用经过验证的清单和单元索引。
提交响应只返回受影响线程。页面复用未变化的卡片，并将列表按每页 100 条展示。
检索和导航覆盖全部线程。文本范围和定位标记缓存避免重复创建及无变化的 DOM 写入。
大请求和响应支持 gzip。可选正文引用避免向发起客户端重复返回其刚提交的长文本。
预检计划保存在 SQLite，提交时在事务内检查修订号、正文、载荷、令牌和有效期。
预检计划使用当前格式版本；旧格式或缺少必要字段的计划失效，须重新预检。升级不迁移短期预检缓存。

## 迁移与正确性

首次迁移在项目锁内校验旧正文、线程及关联。临时 SQLite 完成提交后才原子替换目标文件。
旧 JSON 重命名为 `.json.migrated`。迁移保留修订号、删除记录、全部正文版本、回复、历史和请求收据。
打开旧服务与新服务共用同一项目会导致不同存储路径并存。因此，切换时必须先停止旧工作进程。
运行时不回退到旧 JSON。备份、导出和离线报告保留现有公开契约。
源码替换不能纳入 SQLite 的文件事务。记录或提交失败时，只有源码仍等于本次替换结果才补偿恢复。

## 复测

使用 `scripts/benchmark-annotations.py --help` 查看参数。基准复制正文和全部批注数据，不写正式报告。
`--scale` 先补齐 9900 条线程和 100 个正文版本。每批新增 100 条后达到 1 万条可见线程。
每轮在计时之外删除本轮测试线程，保留删除历史。种子线程分散在不同正文单元。
计时使用浏览器 `performance.now()`。提交完成后等待两个动画帧，将成功状态的绘制计入耗时。
每轮按每秒最多五次提交调度，包含准备和清理请求。P95 使用最近秩法。准备时间和各操作原始样本单独保存。
单客户端场景完成后，再用三个页面轮流提交，每秒合计五次。各客户端先读取增量同步修订号。
同时竞争同一修订号的正确性由事务测试检查，必须恰好一个成功，其余返回冲突。
性能测试必须串行运行，避免多个规模场景互相争用资源。
进程 CPU 和 RSS 数据包含测试程序；浏览器绘制、网络和事务耗时包含在端到端计时内。

实际验收数据保存在本地 `.latex-review/performance/`。生产范围的达标结论只使用最新完成的串行测试。
结果汇总见 [验收记录](annotation-performance-acceptance.md)。
